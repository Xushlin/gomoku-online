## 变异:八处,七处一次就红,一处活了下来

| 变异 | 结果 |
| --- | --- |
| 压牌不看牌型(四头变炸弹) | **活了** → 见下 |
| 压牌不看张数 | 1 红 |
| 3 与 2 不再特殊(退回编码顺序) | 3 红 |
| A 可以进连牌 | 2 红 |
| 连牌 2 组起 | 1 红 |
| 不查每组张数一致(三带一合法) | 1 红 |
| 首叫从最大的梅花开始扫 | 2 红 |
| 挖坑者的输赢符号反了 | 8 红 |

**「四头不是炸弹」那条测试在四头真变成炸弹时照样是绿的。** 去掉「同型」之后 `Beats` 还剩
「同张数 + 更大」,而四头与它想压的东西**张数几乎从不相同**(4 对 3、4 对 2、4 对 1)——
于是每一条断言都因为**别的理由**通过。唯一能区分的形状是**同张数、不同牌型、而且压的那一手
更大**:`KKKK` 对 `4567`(同是四张,K 比 7 大)。补上那一条之后变异变红。

**这是「断言的结论对、判据不对」的又一例**,而它只能被变异测试发现:读那段测试的名字与断言,
它看起来正是在说「四头不是炸弹」。

## 一个 helper 在写完注释几分钟后就踩进了那个坑

测试里的 `Parse("2c")` 写的是 `(CardRank)int.Parse("2")` —— 而 `CardRank.Two` 的值是 **15**,
不是 2:那个枚举的数值是**编码**顺序。于是它得到一个**未定义的枚举值**,`Strength` 的兜底分支
给了它 −1,「2 压得住 A」当场变红。

`hoist-card-model` 里刚写下「数值是编码顺序而不是大小顺序」,而我几分钟后自己踩了进去。
所以那个 helper 现在有一句 `Enum.IsDefined` —— **它不是防御性编程,它是那次踩坑的可执行形式。**
