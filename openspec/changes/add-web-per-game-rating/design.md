# add-web-per-game-rating — design notes

## D1. 为什么 `GET /api/games` 而不是 manifest 上一个 `rated` 字段

见 proposal 的详细论证，此处只记结论与它的判据：

`GameManifest.board` 是服务端数据的刻意副本，能被接受靠两个安全网 —— 失配**肉眼可见**（格数不对），
且服务端 `IsInBounds` 兜底。`rated` 两个都没有：失配的症状是「一个永远空着的榜」，而那与
「新棋种还没人下过」在屏幕上一模一样。

**判据**：一份副本能不能接受，看的不是它有多小，而是**它错了会不会有人发现**。`board` 会，
`rated` 不会。

顺带的收益是它把 `GameManifest.board` 的删除条件从「等 `generalize-match-contract` 把尺寸放上线」
降级成「随时可删」—— 端点已经在传 `Rows` / `Cols` 了。本变更不删（一件事一次），但下一个碰
manifest 的变更可以顺手做掉。

## D2. 榜落在 `/g/:gameKey/leaderboard`，`/home` 那张卡片一个字不动

`/g/<key>` 已经是每棋种的命名空间（`/g/tictactoe`、`/g/idiom-crossword`），榜跟着走一致。

**不碰 `/home` 是刻意的。** 那张卡片是**五子棋大厅**的组件；给它加棋种切换就等于开始泛化大厅，
而 `/home` 在五份 web spec 里是规范路径，泛化它要把那五份一起改写。那是 roadmap 上单独的一步
（等中国象棋，它是第一个真的需要人人对战大厅的游戏）。

副作用要说清楚：**有一段时间会有两个入口看同一个五子棋榜** —— `/home` 的卡片和
`/g/gomoku/leaderboard`。那不好看，但它比「现在就动五份 spec」便宜，且大厅泛化那一步会自然消掉它
（那时 `/home` 的卡片要么参数化、要么就该指向 `/g/:key/leaderboard`）。记为**已知重复**，不是遗漏。

## D3. 「没下过这个棋种」必须和「下过但是 0 分差」长得不一样

后端对没有战绩行的用户返回 200 + 初始值（`Rating = 1200`、战绩全 0），**刻意不是 404** ——
「这个人存在但没下过这个棋种」是正常答案。

但那对 UI 是个陷阱：直接渲染就成了「1200 分、0 胜 0 负」，看起来像一个下过棋的新手，而不是
一个从没碰过这个棋种的人。这两件事在中国象棋刚上线时对**几乎每个用户**都成立，所以不是边角。

规则：`gamesPlayed === 0` 时渲染「尚无对局」空态，不显示 1200 —— 那个数字此刻不承载信息。

（这也解释了为什么后端选 200 而不是 404：404 会被前端误报成「用户不存在」，那是更糟的谎。
DTO 给的是「真值 + 一个能判断真值有没有意义的字段」，判断留给 UI。）

## D4. `LeaderboardApiService.getPage` 的 `gameKey` 必填

与后端 `GetLeaderboardQuery.GameKey` 必填同一条纪律：**服务层不猜自己在被问哪个棋种**，
缺省只发生在调用点。

后端的缺省在 controller，因为那是向后兼容的边界（已发布客户端不送这个参数）。前端没有这层
兼容义务 —— 每个调用点都知道自己在看哪个棋种，让服务替它猜只会把一个「忘了传」变成
「悄悄给了五子棋的数据」。

## D5. 只投影 `IGameRules`，不把谜题混进来

`GET /api/games` 只列对战棋种。谜题类走 `IPuzzleRules`，已经有自己的一条 REST 线
（`/api/puzzles/games/{gameKey}/levels`）。

把两者塞进一个端点会造出一个字段一半为空的 DTO（谜题没有 `Rows`/`Cols`/`IsRated`，
对战没有关卡数），而那种 DTO 的下一步永远是加一个 `type` 字段然后到处 switch。
`CLAUDE.md` 从第一天就写着三个类别刻意不共享一个聚合 —— 端点跟着分。

前端的 `GAME_REGISTRY`（manifest）**仍然是那份把三类游戏并排展示的清单**，因为目录页确实要
并排展示它们。服务端的能力信息按 key 合并进去，合不上的（谜题、未实现的规划游戏）就没有
能力信息 —— 那正确，它们没有 `IGameRules`。
