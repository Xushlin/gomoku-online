# add-mobile-game-catalog

手机端从「一个五子棋大厅」变成「一个有目录的平台」。**这一笔里象棋不出现** —— 它是 `add-mobile-xiangqi` 的地基,两笔拆开是因为象棋那半本身就够大。

## 为什么先做这一半

手机端现在的首屏是五子棋大厅,棋种键是一行常量:

```dart
// lobby_view_model.dart:8
const gameKey = 'gomoku';
```

它当初的注释写着「一个只有一项的选择器是假装成平台的选择器」。要上第二个棋种,先得有那个选择器 —— 而这一笔动的**全是既有屏**,不引入新棋种,所以它自己能验完。

## 三件事

### 一、目录从 `GET /api/games` 读,客户端 MUST NOT 存第二份

那个端点已经把整个注册表投影出来了:

```csharp
public sealed record GameDescriptorDto(
    string GameKey, bool IsRated, bool SupportsHumanVsHuman,
    bool SupportsAi, int SeatCount, int? Rows, int? Cols);
```

盘面行列数、座位数、支不支持人人对战,全从那里来。

这条不是洁癖 —— `GameDescriptorDto` 自己的文档写着为什么:一份 `rated` 副本失配的症状是**一个永远空着的榜**,与「新棋种还没人下过」在屏幕上一模一样,**所以失配不会被发现**。而「手写清单假装成注册表」在这个仓库里修过**八次**,其中一次还出现在为了防这件事而新写的检查脚本里。

`Rows` / `Cols` **可空**,`SeatCount` 不可空 —— 这个区别是服务端 DTO 文档明写的:每个有规则的棋种都有座位数,而成语接龙真的没有盘面。

### 二、目录会列出手机端还画不出来的棋种,而那正好给了这一笔一个不空的判据

服务端返回 **7** 个对战棋种(实测,不是估的),手机端只有一个棋盘。所以目录不能只列自己会画的那些 —— 那就又是一份客户端清单。

做法:**列出服务端返回的每一个**,画不出来的显示为**禁用**。而「哪些画得出来」这个事实 SHALL 从**棋盘注册表**派生(一处),MUST NOT 是一份手写名单。

于是这一笔有了一个两边都不空的走查:**启用的条数 == 棋盘注册表的条数**,且**至少有一个禁用的**。两个方向都在样本里,不是「至少一个」那种一边倒的断言。

测试里再钉一个**今天的数字**(恰好 1 个启用)。`add-mobile-xiangqi` 落地时它**应该红** —— 那正是想要的:数字变了得有人看见。

### 三、`size` 那个参数不只是没验证过,它还假设了正方形

```dart
GomokuBoard({..., this.size = 15});   // 一个数
for (final r in const [3, 7, 11]) {}  // 星位,只对 15 路成立
```

象棋是 **10×9**,一个数表达不了。**一个只有一个调用方、而那个调用方永远传同一个值的参数,不是参数,是一句没人验证过的承诺。**

拆成 `rows` / `cols`,尺寸从描述符来。装饰按尺寸判断,而**判据是「非正方形不画出界的点」**,不是代码看起来对。

顺带修一处注释:类文档说间距是 `size / (n - 1)`,代码是 `side / size` 加半格内缩 —— **代码对、注释错**,一句写错的公式会把下一个人送错方向。

**这里有一处要老实说:这一笔之后 `rows != cols` 仍然没有生产调用方。** 一个只有测试在用的能力和一句空承诺只差一步。区别在于**下一笔已经指名了那个调用方**(象棋 10×9),而且是同一轮里的下一笔 —— 不是「以后」。**如果 `add-mobile-xiangqi` 不做了,这一半就该退回去。**

### 四、路由三层化 —— 上一笔那个嵌套的第一次复用

```
/login
/                            棋种目录
/games/:key                  该棋种的房间列表(大厅)
/games/:key/rooms/:id        一局棋
```

`add-mobile-router` 里量过:把子路由改成顶层路由,**编译通过、分析零问题、`redirect` 照旧**,而房间里 `canPop()` 立刻变 false、`AppBar` 一个返回按钮都不画。判据照抄 `canPop`,两个方向都要 —— 目录里 `canPop()` MUST 为 false,否则已登录的人按返回会退回登录页。

盘面尺寸取自**房间快照的 `gameKey`**,不取自路由里的 `:key`。`RoomStateDto` 的文档把理由写全了:进房间有四条路(建房跳转、刷新、收藏链接、从「我的对局」进),**只有第一条上客户端知道棋种**。

## 与 `add-mobile-xiangqi` 的关系

两笔都只 **ADDED** 到 `mobile-shell`,**没有 MODIFIED** —— 因为 MODIFIED 会整条替换,两个未归档变更碰同一条要求就得手工合。为此第一笔的判据写成**派生的不变量**(「启用条数 == 棋盘注册表条数」),而不是一个第二笔必须来改的数字。

**归档顺序:先 `add-mobile-game-catalog`,再 `add-mobile-xiangqi`。**

## 不做

- **象棋。** 下一笔。
- **手机端排行榜。** 目录里会显示哪些棋种计分,但榜是另一屏加一个 API。触发条件:第一个计分棋种能在手机端下起来 —— 也就是 `add-mobile-xiangqi` 落地之后。
- **一字棋。** 它 `supportsHumanVsHuman: false`(注册表里唯一的一个),要人机房。触发条件:手机端第一个只有人机入口的棋种 —— 已经指名是它。
- **深链接。** 触发条件仍是「第一个会产生房间链接的功能」。

## 规模

目录仓库 + 模型、目录屏、路由三层化、大厅去硬编码、几何抽取。**估计 350–450 行**,可能刚好卡在准则线上;超了我在 PR 里报数字。
