# add-mobile-room-exit

手机端**从来没有真正离开过房间**。补上那条出口,以及它缺失带来的三个后果。

## 量出来的四件事

### 一、`/leave` 和 `/dissolve` 一次都没被调用过

`frontend-mobile/lib` 里搜 `leave` / `dissolve`,**七处命中全是注释里的散文**,没有一处是调用。hub 的 `LeaveRoom` 也是 0 次。

所以按下返回箭头只是 pop 了一个路由:**服务端那边你还坐在那个座位上,永远。** 一个等待中的房间因此永远等待 —— 而它的房主(你)在客户端上没有任何办法解散它,因为服务端对「等待中房间的房主走 `/leave`」是明确拒绝的(`HostCannotLeaveWaitingRoom`),必须走解散那条路(`DELETE /api/rooms/{id}`)。

### 二、`RoomDissolved` 被忽略

服务端在房主解散时推它,**而解散之后不会再有 `RoomState`** —— 房间被物理删除了。所以别人解散时,手机端把人**留在一个已经不存在的房间里**:盘面还在,点哪儿都是错误。

### 三、`RoomRepository.close()` 没有生产调用方

它会摘掉监听、停掉 hub、dispose `_live`。**没有人调它。** `GameViewModel.dispose()` 只摘掉自己那一个监听器。

这不只是「没清理」。`open()` 每次都 `_hub.state.addListener(_republish)` 而**没有任何地方 remove** —— 进过五个房间就注册五次,每条推送把 `Room.fromJson` 跑五遍。今天无害(它是幂等的),而无害恰好是这种东西活下来的方式。

### 四、于是有一个**真会被看到**的 bug,而它是上一笔刚刚「解锁」的

因为从不调 `LeaveRoom`,客户端**留在它进过的每一个房间的 hub 分组里**。于是:

1. 进房间 A、退出、进房间 B
2. 有人在 A 里走了一步
3. 服务端把 A 的 `RoomState` 推给 A 组 —— 客户端还在里面
4. `_republish` 把 `_live` 设成 **A** 的快照
5. **你在 B 里,盘面显示的是 A**

**这个 bug 在 `fix-mobile-hub-inbound` 之前不可能发生** —— 那时一条推送都到不了。**「不调 LeaveRoom」这件事在入向是死的那段时间里是无害的,而修好入向让它变成了活的。** 一个结论可以在支撑它的前提变假之后仍然看起来没问题。

## 改什么

### 出口要告诉服务端,而走哪条路由服务端的规则决定

- 一般情况:`POST /api/rooms/{id}/leave`
- **等待中房间的房主**:**`DELETE /api/rooms/{id}`** —— 服务端对这种情况的 `/leave` 是 409 拒绝的(「dissolve it instead」),这不是客户端的偏好
- 两条都要:hub 的 `LeaveRoom`(退出分组),以及摘掉 `_republish`

**这一段的第一版把解散写成了 `POST /api/rooms/{id}/dissolve`,而那条路由不存在** —— 实测 404。改对了,并且补了一条从 controller 特性里抠路由的走查。

**判据不是「调用返回 200」,也不是「座位空了」** —— 实测**两种状态下离开都不腾空座位**,所以普通 `/leave` 没有服务端可观测的变化。判据是**那个分支**:房主离开等待中的房间 → 房间不见了;其他任何人 → 房间仍然存在。

### 离开一局进行中的对局要先问

`game.leave-confirm.*` 的文案包里全都有(`title` / `leave` / `stay` / `match`),web 端也是这么做的:**离开不会结束这一局,座位仍然是你的,但回合计时继续走**。一个静默的出口在这种语义下是错的。

用 `showDialog`(Flutter 这边的 CDK 对应物 —— 焦点陷阱与返回键由框架给)。**等待中的房间不问** —— 与 web 端同一条判据,而不是另写一条:两条规则会分叉,而分叉的表现是某条路径悄悄不问了。

### `RoomDissolved` 要把人送出去

订阅它,导航回该棋种的大厅。web 端就是这么做的(它把所有人、包括围观者都送回 `/home`)。

**这会让 `hub_contract_test` 的订阅数从 2 变成 3** —— 那条走查断言的是「订阅的 ⊆ 服务端发的」,所以它会继续绿。**顺带说清一件事:那条走查是一边倒的**,它对「服务端发的里哪些*该*订阅」一个字都没说,而那一半没法机械推导 —— 十个里七个不订阅是对的(`MoveMade` / `PlayerJoined` / `PlayerLeft` / `Spectator*` 的信息 `RoomState` 全带着;`ChatMessage` / `UrgeReceived` 对应的功能手机端还没有)。**这一笔只补那一个真缺口,不去追平 10/10。**

## 不做

- **聊天与催促**(`ChatMessage` / `UrgeReceived`)—— 功能本身手机端没有。触发条件:哪一个功能上手机端。
- **认输**。它是 `Playing` 状态的出口,与本笔的「离开」是两件事,而三座位棋种的认输在平台上本来就还欠着(见 CLAUDE.md 那张表)。触发条件:手机端要在进行中的对局里直接结束一局。
- **追平 web 端的 10/10 订阅**。见上。

## 规模

出口(两条路由 + hub + 监听器)、确认弹窗、`RoomDissolved`、以及那个重复注册。**估计 250–350 行**,大头是测试 —— 而它们必须对着真后端跑:这一笔里**两个判据都是被真服务端推翻的**(解散的路由、以及「座位会空」),而单测对两个都是绿的。
