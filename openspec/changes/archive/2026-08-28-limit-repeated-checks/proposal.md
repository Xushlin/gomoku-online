# limit-repeated-checks

一条棋理限制:**同一个将军最多重复三次,第四次不许再走。**

## Why

用户要的。而它落在象棋上有一个具体的理由:平台此刻**没有任何**重复局面规则,于是一方可以
无限长将 —— 对手永远在应将,棋永远走不完,而界面上一切正常。

### 判据:局面,不是走法

**「将军」是局面的性质,不是那一步的性质。** 所以「同一个将军送出了 N 次」与「同一个局面出现了
N 次」是同一句话,而后者不需要为每一步额外记一个布尔。少一份记录,少的是一份会和局面本身
漂开的第二真源。

局面的身份**就是盘面**。象棋里没有王车易位 / 吃过路兵那类额外状态,所以「盘面 + 轮到谁」是
局面的全部;而**「轮到谁」在这一处不必再算进去** —— 计数只在对手被将的局面上进行,而一个
「对手被将」的盘面只可能由本方走出来:对手走到那儿等于把自己的将留在被吃的位置,那一步早被
自将规则挡掉,进不了历史。

**这一条是变异测试改的,不是想出来的。** 第一版写了「只数本方走出的局面」,而五条变异里
**只有它活了下来** —— 没有任何断言能让它红。删掉它靠的是自将必被拒,而那条规则自己有测试。
一个靠有测试的规则支撑的删除,好过一个没有断言覆盖的分支。

### 上限 3 是哪三次

允许第 1、2、3 次,拒绝第 4 次。两端都钉:只钉一端时,一个把上限写成 0 的实现和一个写成 99 的
实现各能通过其中一条。

### 将死优先,而这两条其实不冲突

一步**将死**的着法必须判胜,哪怕它达到了上限。而它们不会真的撞上:局面相同 ⇒ 合法着法集合
相同 ⇒ 若此刻将死,此前那次也将死,棋在那时就该结束 —— 所以一个将死的局面**不可能**有过往
出现。顺序仍然写成「先判将死」,是为了让这段论证不必成为正确性的前提。

### 为什么是「拒绝一步棋」,而不是判和或判负

用户说的就是「不能再走了」。而这不是一条悬在空中的规则 —— 有人会问:如果一方**只剩**这一步呢?

那他确实一步也走不了,而**收场的东西早就在**:`TurnTimeoutWorker` 判走不了的一方负。
那正是传统的长将判负。同一条推理这个仓库已经用过一次(`GameKeyValidation` 里,给一个走不了的
局面):**60 秒后超时判负**。所以不需要为这个角落新造任何东西。

### 一处必须一起收紧的地方,而它不是新决定

`XiangqiRules.LegalMoves(history, side)` 是 AI 的着法来源。`ai-opponent` 那条要求的 Scenario
已经写着「每一条都能被 `Apply` 接受」——**所以 `LegalMoves` 不跟着收紧,是让一条已经存在的
要求变假**,而表现是「机器人走出规则会拒绝的棋」,用户看到的是它卡住了。

自将 / 照面是**局面**的性质,`LegalMoves` 本来就在算;重复将军是**历史**的性质,而
`LegalMoves` 恰好收得到历史。所以这次要把「这一步是不是一次被禁的重复将军」抽成
**`Apply` 与 `LegalMoves` 共用的一份判断**。

搜索内部那份按盘面枚举的入口(`LegalMovesOnBoard`)收不到历史,深层节点因此不懂重复 ——
那是**棋力**问题不是合法性问题:真正走出去的只有根节点那一步。这句话要写下来,因为
「AI 内部有一份不懂长将的枚举」读起来像缺陷,而它是刻意的。

### 两个棋种一起,而这是免费的

规则落在 `XiangqiRules.ApplyOn` —— 标准开局与残局共用的那一份(`play-from-position` 抽的)。
所以 `xiangqi-endgame` 自动受限,而残局正是长将最常出现的地方。

### 落子类棋种不给

五子棋 / 一字棋的盘面单调增长,同一个局面**不可能**第二次出现。一条永不触发的规则是每个
读代码的人都要付一次的税。

## 这个变更会推翻一条已经写下的理由

`xiangqi` 有一条要求:**「界面 MUST 说清楚平台认不出和棋」**。它的理由原文是

> 理由是领域里没有重复局面 / 长将 / 长捉规则

本变更之后这句话**是错的**:领域里有了重复局面计数,也有了一条长将规则。而**结论仍然对** ——
这条规则只用来**拒绝一步棋**,不用来**宣布**一个结果。

**一个正确的结论可以在支撑它的前提变假之后继续正确,而那正是它看不见的原因** —— 界面上什么都
没坏,没有任何测试会红。所以这条要求要改的是**理由**:剩下的账是长捉 / 长拦规则、
「重复到第几次算**和**」(与「第几次不许再走」是两个不同的判据),以及一个宣布和棋的决定。

同理,`CLAUDE.md` 那张推迟表里的那一行也要改 —— 它的触发条件写着「长将 / 重复局面规则落地」,
而本变更**部分**兑现了它:机制有了,和棋没有。不改它,下一个人读到的是一句已经被推翻的
「领域里没有重复局面 / 长将 / 长捉规则」。

## 顺带修一个第八次出现的老陷阱

`hub-error.mapper.spec.ts` 里那条「每个码在两个 locale 里都有文案」的走查,遍历的是一份
**手抄的码清单**,而不是映射表本身。手抄的那份**漏了三条接龙的码**。

这不是顺手打扫:本变更要加的 `repeated-check` 如果只进映射表,**那条走查不会覆盖它** ——
少了文案的表现是界面上显示 `game.errors.repeated-check` 这个键本身,而没有任何断言会红。
所以让它从表里派生,是本变更被覆盖的前提。

(这是这个仓库记名的那条陷阱「一份手抄清单冒充注册表」的**第八次**。前七次的教训是:
修了一处就去 grep 兄弟。)

## What changes

**Domain**

- `XiangqiRules`:新增具名上限常量;`ApplyOn` 在判过将死之后判上限;`LegalMoves` 用**同一份**
  判断过滤。重放走一份实现 —— 计数需要每一步之后的局面,而重放的循环 MUST 仍然只有一个。
- `XiangqiBoard`:一个盘面相等判断(90 格逐格比)。
- `InvalidMoveException.RepeatedCheck(...)` 工厂 → 码 `repeated-check`。既有的「码全局唯一」
  走查已经覆盖工厂,所以这个码自动进入那条断言的范围。
- `XiangqiAi` 的「无着法」报错文案:此前断言「棋早该结束了」,那句话在上限存在之后不再是唯一
  解释。

**Web**

- `hub-error.mapper.ts`:一行映射 + 联合类型一项 + 导出码清单供走查派生。
- `zh-CN.json` / `en.json`:`game.errors.repeated-check`。
- 象棋棋盘**一行不改** —— 它刻意不判合法性(`web-xiangqi` D2),所以服务端的拒绝是玩家了解
  这条规则的途径。

## Non-goals

- **不判和棋。** 长捉 / 长拦 / 重复局面判和都不做,理由见上。
- **不改 `IGameRules`。** 这条规则完全在象棋内部,内核不需要知道有「重复局面」这回事。
- **不给 AI 的搜索加历史。** 根节点过滤已经保证它走不出被拒的棋;让搜索懂重复是棋力,
  而棋力不是这次要买的东西。
- **不做「六十步无吃子判和」。** 那是另一条规则,也是另一个判据。
