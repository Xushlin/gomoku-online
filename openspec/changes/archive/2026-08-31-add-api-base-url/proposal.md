# add-api-base-url

客户端不再假定「服务器就在同一个源上」。**桌面壳的第一步,而手机端将来走同一条。**

## Why

用户要桌面客户端。而在写任何 Electron 代码之前,有一件**量出来的**事挡在前面。

### 今天的前端连不上任何远程服务器,一行都不行

```
frontend-web/src/app 里所有绝对 URL:  0 条
REST:  '/api/…'          同源相对
Hub:   '/hubs/match'     同源相对(GAME_HUB_URL)
src/environments/        不存在
```

浏览器里这没问题 —— dev 有 proxy,生产同源部署。**而 Electron 把页面装在本地**(`file://` 或自定义协议),那时**没有「同源」这回事**,每一个 `/api/…` 都会打到一个不存在的地方。

所以这不是「为将来铺路」——**不做它,桌面壳的第一次登录就失败**,而且失败得很难看:一个 404 的相对路径,看起来像后端挂了。

### 服务端那一半早就准备好了,这是有利的证据

`Program.cs` 里已经有 `AddCors` + `WithOrigins(corsOptions.AllowedOrigins)`,配置项也在 `appsettings.json` 里。**当初就预料到会有跨域客户端**,只是从来没有过一个。所以本变更后端**一行不改**,只在部署时往那个列表里加一项。

### 为什么单独成一个变更,而不是塞进 Electron 那个

三条理由,而第一条是决定性的:

1. **手机端将来要用同一样东西。** 它是两条路的公共前提,不是桌面的实现细节。塞进 Electron 里,等 Flutter 来的时候要么再抽一次,要么复制一份。
2. **它自己可测,而 Electron 那个不容易。** 「base URL 可配置」是一条纯粹的前端断言;「Electron 窗口里能登录」需要一个打包好的壳。
3. **它有一条强不变量,而那条不变量值得单独钉住**:见下。

## 核心不变量:Web 端的行为 MUST 一个字节都不变

默认值是**空字符串**,拼出来仍然是 `'/api/rooms'`、`'/hubs/match'` —— 与今天逐字节相同。

这条不是客套。**改动的是每一个 HTTP 调用和唯一的实时连接** —— 平台上没有比这更宽的改动面了。一个静默的行为变化会表现成「某个页面偶尔加载不出来」,而那种缺陷要几周才会被归因回这里。

所以验收判据是可执行的:**既有 87 个 spec 文件、1042 条测试,断言一条不改地通过**。它们里面大量 `expectOne('/api/rooms')` 这样的精确 URL 断言 —— 那批断言就是这条不变量的可执行形式,而**它们已经存在了**,不用新写。

## What changes

- 一个 DI token:`API_BASE_URL`,默认 `''`。
- `core/api/` 下所有服务与 `GAME_HUB_URL` 的消费者从它取前缀。**HTTP 只在 `core/api/` 里发**(既有硬规则),所以调用点是收敛的。
- 一处 provider,让宿主(Electron / 将来的手机端 / 测试)覆盖它。
- **后端零改动。**

## Non-goals

- **不做部署。** 服务器部署在哪是另一笔账,而它不挡桌面壳的开发(桌面壳可以指向本地 dev 服务器)。
- **不动认证。** token 仍然在 `localStorage`;Electron 里那是否够好是壳那个变更要答的。
- **不做离线。** 见下。

## 而用户要的三样里,有两样这条路给不了 —— 写下来,免得下一个人以为它们在路线图上

- **「上应用商店」** —— Electron 能上 Microsoft Store / Mac App Store,**上不了 iOS 与 Google Play**,那需要原生(Flutter)或 Capacitor 包一层。
- **「离线也能玩」** —— 这一条与平台的授权模型**相反**,不是工期问题:成语纵横与猜成语的 `solutionJson` **永不出服务端**(`web-idiom-guess` 明写「客户端不持有答案,也不自行计分」),华容道**重放每一步**才算通关,俄罗斯方块结束时由服务端验分,六个对战棋种本来就要服务器,而**登录本身**也要 API。离线判题等于把答案发到客户端 —— 那是动三个内核之一,该是一个独立的、需要理由的决定。
