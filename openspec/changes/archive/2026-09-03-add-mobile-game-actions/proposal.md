# 手机端的房间动作条:认输与催促

## 为什么

房间里现在只有一件事能做:落子。**认输**和**催促**服务端早就有,而手机端一个入口都没有。

两件都不是新能力,而是两条够不着的能力 —— 和「换不了主题」同一个形状:

| | 服务端 | 手机端 |
| --- | --- | --- |
| 认输 | `POST /api/rooms/{id}/resign` → `GameEndedDto` + `GameEnded` 推送 | 没有入口 |
| 催促 | hub `Urge(roomId)` → `UrgeReceived`(仅被催方) | 没有入口,也没有订阅 |

**催促这条在动工前先量出了一个服务端缺陷**,已由 `fix-urge-user-routing` 单独修掉:`Clients.User(...)` 没有 `IUserIdProvider`,推送寄给了没人登记的地址。**这一笔依赖那一笔**——否则催促按钮天生是死的,而且死得不报错。

## 做什么

### 认输

- 入口出现的条件是**三个**:我是这局的玩家、对局进行中、**这个棋种恰好两个座位**。
- 第三个条件读的是**房间自己的 `seatCount`**,不是棋种目录 —— 被认输的是这个房间。它不是保守,是**平台的实际限制**:`Room.Resign` 需要恰好两个座位才能指出赢家,三座位棋种上是 409。这条已经让 web 端付过一次 **500** 的代价(`fix-three-seat-resign`),而当时的原因正是「客户端假设了座位数」。手机端现在只有两个两座位棋种,所以**这个判据今天恒真** —— 它写下来是为了第三个棋种落地那天不用重新发现。
- 不可逆,所以**先确认**。文案 `game.actions.resign-confirm-*` 已在同步产物里。
- **认输之后 MUST NOT 自己宣布结果。** 结果走 `fix-mobile-game-over` 已经铺好的那一条路(快照的 `result` / `GameEnded` 推送)。两条宣布结果的路会分叉,而分叉的表现是其中一条说错了赢家。

### 催促

- 入口出现的条件是:我是玩家、对局进行中。**可点**的条件再多一条:**不是我的回合**。
- 不能点时说明**为什么**,两个不同的键(`game.urge.button-disabled-own-turn` / `-cooldown`)——「按钮是灰的」不是解释。
- **客户端 MUST NOT 自己算 30 秒冷却。** 它可以在收到 429 之后把按钮按住一会儿,但「服务端会不会接受」这个结论由服务端给。一份并行的冷却计时器是第二处规则,而两处规则会分叉。
- 收到 `UrgeReceived` 时屏幕上要有反应(`game.urge.toast`),**且不需要刷新** —— 这是个推送,不是快照的一部分。

### 一个键都不新增

上面每一条文案都已经在 `assets/i18n/*.json` 里(从 web 端同步来的)。新增键会让 `shared_sync_test` 红,那是对的。

## 不做

- **三座位棋种的认输。** 平台上还没有这个能力(欠账表里那条等的是「积分梯度」),而手机端也还没有三座位棋种。
- **聊天与围观。** 各自独立一笔。
- **催促的音效。** 这个客户端没有音频层。
