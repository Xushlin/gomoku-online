# add-doudizhu-play-hints

## Why

`add-wakeng-play-hints` 把「要不起自动过牌」与「提示按钮」给了挖坑,并写下了触发条件:

> **触发条件:斗地主也要这两个功能的那天**,而那时该问的是「这两个棋种的『出得起』真是
> 同一种东西吗」——今天的答案是**不是**。

触发条件到了。**问题问过了,答案仍然是「不是」**,而这次要说清不是在哪里。

## 「出得起」在两个棋种里不是同一种东西

| | 挖坑 | 斗地主 |
| --- | --- | --- |
| 跨型压 | **没有** —— 没有炸弹,`Beats` 要求同型同张数 | 炸弹压任何非炸弹、王炸压一切 |
| 带牌 | **没有** —— 三头四头都不能带 | 三带一 / 三带一对 / 四带两单 / 四带两对 / 飞机带单翅 / 飞机带对翅 |
| 候选的形状 | 「同一种牌型里更大的那些」 | 「同型更大的」**并上**「任何一个炸弹」 |

挖坑的枚举是「k 组等大的牌」一句话覆盖八种牌型;斗地主有十三种,其中六种带**填充牌**。
两边没有一行可以共用的枚举逻辑。

**所以枚举各写一份**(与 `WakengMove` 不复用 `DoudizhuMove` 是同一条判据:形状相同不等于
事实相同),**而接缝共享** —— 因为那才是真正相同的那件事:*给我手牌和桌面,列出我能出的*。

## What changes

### 一个新接缝(第五次用同一个模式)

```
public interface IPlayHintRules : IGameRules
{
    IReadOnlyList<string> LegalPlays(MatchState state, int seat);
}
```

- 返回的是**牌的编码串**(`play:` 后面那一段),对内核**不透明** —— 与 `ViewFor` /
  `CreateSetup` / `LayoutJson` 同一个做法:内核不该知道什么是牌。
- **单独一个接口**,而不是给 `IGameRules` 加成员。理由与 `IDealtGameRules` /
  `IPerSeatViewRules` / `IFirstSeatRules` 当初分出来时逐字相同:留在基接口上,另外五个棋种
  就得各写一个骗人的实现,而**骗人的实现是下一个人删不掉的东西**。
- `GetPlayHintsQueryHandler` 因此**不再写死棋种键**:它按注册表解析规则,解不出这个接口就
  返回空。**那是这个变更真正必须做的事** —— 加第二个游戏而不加接缝,Application 层就会
  长出一个 `switch (gameKey)`,而这个仓库明写着「实现 MUST NOT 内联任何『哪些棋种存在』的
  硬编码列表」。

### `DoudizhuFollows`

斗地主自己的枚举。它比挖坑那一份多两件事:

1. **炸弹与王炸永远在候选里**(桌上不是炸弹时),而且它们跨型 —— 所以候选不是「一种牌型
   里的一段」,而是两部分的并集。
2. **带牌的那六种要选填充牌**,而那带来一个真问题,见下。

### `canFollow` 进 `DoudizhuSeatView`

与挖坑同一个定义:「假如此刻轮到你,你出得起吗」,与轮次无关。客户端那份共享的
`CardTableView.canFollow` 已经在,而斗地主的配置今天把它写死成 `false`(「没有这个信号」)
—— 这个变更让它读真值。

## 一处真判断:带牌的候选**只列一条**,填充牌取最弱

一手 20 张牌里有一个三条,`三带一` 的变体有十几个 —— 它们**只有填充牌不同**,而
`Beats` 只看三条。全列出来,提示按钮就变成「在同一个三条的十五种写法里轮换」,那不是提示。

所以:**同一个「决定大小的部分」只出一条候选,填充牌取手上最弱的那些**。

- 它是一处**判断**,不是推导 —— 所以它有名字、有理由:填充牌是要扔掉的东西,而扔掉最弱的
  是默认最优。
- 它有代价,写下来:一个想拿 `333 + 一张 K` 去骗对家的玩家,提示不会给他那一手 ——
  而他仍然可以手工点。**提示是建议,不是代打。**
- 一条断言钉住它:候选里 `三带一` 的条数 == 手上可用三条的条数(而不是三条数 × 单张数)。

## 不做什么

- **挖坑那份枚举一行不改。** 这个变更的验收标准之一是 `WakengFollows.cs`
  在 `git diff --name-only` 里**不出现**。
- **不合并两份枚举。** 上面那张表就是理由;而「它们可以分歧」正是「这不是一个事实」的检验。
- **不改客户端的自动过牌与提示按钮本身。** 它们按配置驱动,所以斗地主的 `seatView`
  一旦真的带上 `canFollow`,那两个功能就生效。

  **但「客户端零改动」这句话我写错了,而错法值得记。** 斗地主那份 adapter 里
  `canFollow` 是**写死的 `false`**,注释还写着「斗地主还没有这个功能 —— `false` 在这里是
  『没有这个信号』」。也就是说那个占位符**本来就在等这一天**,而我在写提案时把「参数化过了」
  记成了「不用改」。真实代价是**一个字段、一处解析、一处 adapter** —— 比零大,比重写小。
  参数化的回报是真的,只是它的单位不是零。

## 验收

- **两个棋种都要有那条「两个出口一致」的断言**:`canFollow == (LegalPlays(...).Count > 0)`,
  逐座位、逐局面。
- 斗地主特有的断言:**炸弹压得住任何非炸弹**(所以手里有炸弹时 `canFollow` 恒真)、
  **四带二不是炸弹**(它压不住同张数的别的牌型)、**顺子只与同长度比**。
- 「要不起」那条 MUST 用一个**真的要不起**的局面 —— 而斗地主要构造它比挖坑难:
  手里**不能有炸弹**,否则永远出得起。这条前提 MUST 被显式断言,否则那条测试会因为
  别的理由通过。
- 一条**注册表走查**:实现 `IPlayHintRules` 的恰好是两个牌类棋种,而其余棋种一个都不实现。
- 变异:handler 忽略接缝(恒返回空)MUST 红;带牌候选改成全列出 MUST 红;
  炸弹不进候选 MUST 红。
