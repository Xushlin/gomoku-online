# add-mobile-xiangqi

手机端第二个棋种 —— 中国象棋。**依赖 `add-mobile-game-catalog`**(目录、三层路由、`rows`/`cols`),它先落地。

## 为什么是象棋而不是一字棋

一字棋 `supportsHumanVsHuman: false` —— 注册表里唯一的一个,`GameKeyValidation` 会用 400 拒掉给它建的人人房。上它就得先有人机房,而手机端一个都还没有。象棋反过来:

```csharp
// XiangqiRules.cs:75,93
public bool SupportsHumanVsHuman => true;
public bool IsRated => true;
```

**便宜的一半:不需要人机房。** `POST /api/rooms` 那条路已经在跑。
**贵的一半:棋盘是真的。** 10×9、子落在交叉点上、河界九宫、走子 `from → to`、hub 是另一个方法。

## 三件调查出来的事

### 一、服务端不下发局面,客户端要自己重放 —— 而重放不需要规则

`GameSnapshotDto` 只有 `Moves`(每步 `{Ply, Row, Col, Seat, FromRow?, FromCol?}`),没有任何盘面字段。所以画盘 = 初始摆法 + 逐步 `from → to`。

web 端那份重放**一共 19 行(含签名与边界检查),一条规则都没有**,真正改变状态的是两行:

```ts
// position.ts:134 positionAfter
cells[to] = cells[from];
cells[from] = null;
```

**这不违背「客户端 MUST NOT 自行判定走子合法性」那条要求,而是它的另一面** —— 重放连「马走日」都不知道:谁在 `from` 上就搬到 `to`,`to` 上原来有谁就消失。要移植的是这 19 行、一份初始摆法(从一个后排次序列表加镜像对称推出来,**不是手打 32 个格子**)、和 14 个字形。

**初始摆法怎么防抄错:不跟另一份副本比,跟权威比。** 集成测试下一步真实开局(炮二平五)并要求**服务端接受**它 —— 客户端对「那个炮在哪」的看法一旦和服务端不一致,这一步会被拒。**两份客户端副本可以一起错,服务端不会陪着错。**

### 二、`Stone.Black` 在象棋里是**红**方,而这条规则栽过一次

```ts
// position.ts:38
export const RED: XiangqiSide = 'Black';
export const BLACK: XiangqiSide = 'White';
```

`Game` 从 `Stone.Black` 开局,象棋红先,所以 `Black` 读作红。web 端把它做成两个**命名常量**,注释写明理由是「不让任何地方出现裸的 `=== 'Black'`,因为那正是将来有人来『修正』它的地方」。

`CLAUDE.md` 记着它栽过:`web-game-board` 曾把「象棋读作红 / 黑」写在**括号里**,没有实现读它、没有测试守它,而同一条要求下面的 Scenario 还明说「侧栏说『黑方 / 白方』」—— 三处代码照着 Scenario 写,象棋房把红方叫成黑方,活了很久。**一个写在括号里的例外和没写是一样的:例外要么变成判据,要么删掉。**

还有一处更细的:同一次调查发现,当初那条判据被写成了**按座位数分**(「座位数大于二 → 说座位号」),而它的**理由**是「『白方走棋』在一个没有白方的棋种里是错的」。象棋和五子棋都恰好是两个座位,于是该拦的从缝里过去了。**这一笔的判据贴着理由写:读法按棋种分,不按座位数分。**

### 三、测试上有个坑,它同时是交互设计

**点自己的子是「重新选中」,永远不会变成一步走子。** 所以「往自己子上走」测不出服务端拒绝 —— 什么都没发出去。要测服务端拒绝,落点必须是**空格或敌子**。

这也是唯一能确认「客户端没有偷偷自己判合法性」的路:选一个该子走不到的**空格**,客户端 MUST 把它发出去,由服务端拒。

## 走子:hub 是另一个方法

```csharp
public async Task MakeMove(Guid roomId, int row, int col)                              // 五子棋
public async Task MovePiece(Guid roomId, int fromRow, int fromCol, int row, int col)   // 象棋
```

**是另一个方法而不是给 `MakeMove` 加参数**,因为 SignalR 不套用 C# 可选参数缺省值:客户端多送或少送参数都会在**绑定层**被拒 —— 早于任何 filter,且低于配置的日志级别,所以**两头都看不见**。给活着的 hub 方法加参数是破坏性变更;加方法不是。

## 这一笔会让上一笔的一个数字变红

`add-mobile-game-catalog` 在目录走查里钉了一个「**恰好 1 个启用**」。象棋落地后是 2。**那正是它该红的时刻** —— 改数字的时候顺手确认新那条也进了棋盘注册表,而不是绕过注册表硬塞进目录。

同理,那一笔写在类注释里的欠账(`rows != cols` 没有生产调用方)**在这一笔里兑现**。

## 不做

- **手机端排行榜。** 象棋计分,所以这是第一次**有可能**做。触发条件:这一笔落地之后你想看榜。
- **象棋残局 / 古谱。** 独立的键、要 `ChosenSetup`、要一份 1634 局的库。
- **人机对战。** 象棋有 AI,但手机端一个人机房都没有。触发条件:第一个只有人机入口的棋种上手机端 —— **一字棋就是那个**。
- **深链接。** 触发条件仍是「第一个会产生房间链接的功能」。

## 与 `add-mobile-game-catalog` 的关系

两笔都只 **ADDED** 到 `mobile-shell`,**没有 MODIFIED** —— MODIFIED 会整条替换,两个未归档变更碰同一条要求就得手工合。**归档顺序:catalog 先,本笔后。**

## 规模

局面重放、初始摆法、象棋画笔(河界 / 九宫 / 14 个字形)、选中交互、第二个 hub 方法、红/黑读法。**估计 400–500 行**,大头是画笔和测试。
