# add-web-tictactoe-ai — design notes

## D1. 盘面尺寸放在前端 manifest，而不是从服务端下发

棋盘要画几格，两个来源都成立：

**(A) DTO 只带 `gameKey`，前端从自己的 `GameManifest` 查尺寸。** 选了这个。
**(B) DTO 带 `gameKey` + `rows` + `cols`，服务端说了算。** 没选。

(B) 在设计上更干净 —— 单一真源，客户端甚至能渲染一个它的 manifest 里没有的棋种。代价是 `ToState` 需要 `IGameRules`，而调用 `ToState` / `ToSummary` 的地方有九处（`GetRoomState`、`JoinRoom`、`LeaveRoom`、`MakeMove`、`CreateRoom`、`CreateAiRoom`、`JoinAsSpectator`、`LeaveAsSpectator`、`GetMyActiveRooms`…）。为了两个整数把注册表穿过九个 handler，换来的是一个「我想玩上」的变更膨胀成一次映射层重构。

选 (A) 的三个具体理由，而不是「省事」：

1. **重复是有界的，而且是已存在的那一类。** 前端 `GAME_REGISTRY` 早就在镜像平台知识（`key`、`category`、`icon`、`contentLocales`）。再加 `board` 属于同一类，不是新开了一个失配面。
2. **失配的症状立刻可见。** 前端把 3×3 写成 4×4，第一眼就是棋盘格数不对 —— 不是那种潜伏三个月的错。对比 (A) 的真正风险其实很低。
3. **失配伤不到数据。** 服务端 `rules.IsInBounds` 已经挡住越界落子（`add-game-rules-registry` 把上界从 `Position` 移到规则那次的直接收益）。一个画大了的客户端棋盘点下去只会拿到错误，不会写坏对局。

`generalize-match-contract` 反正要重写这两个 DTO（座位、JSON 载荷），(B) 该在那时一起做 —— 那时穿注册表的成本已经被别的需求付掉了。

## D2. `gameKey` 进 DTO 是阻塞项，不是顺手改动

值得写清楚，因为它看起来像「一个纯前端变更里夹带的后端改动」。

玩家进棋盘有四条路：从 `/g/tictactoe` 建房跳过去、刷新页面、点收藏链接、从「我的对局」卡片进来。只有第一条路上客户端知道棋种（是它自己刚选的）。后三条它手上只有一个 room id。

所以「棋盘尺寸从路由参数带过来」这条捷径是假的 —— 它只在四条路里的一条上成立，另外三条会画成 15×15。DTO 必须说出棋种。

`Room.GameKey` 从 `add-tictactoe` 起就存在且已填好，映射不需要任何新依赖，改动是每个 record 加一行、每个 mapping 加一行。

## D3. 人机局不让玩家起房间名

后端 `CreateAiRoomCommand` 要求 `Name` 3–50 字符（与人人房间共用校验）。人人房间需要名字：它要出现在大厅列表里给别人认。

人机房间**不出现在任何列表里** —— `GetRoomListQuery` 按棋种过滤，而一字棋没有大厅；`/home` 是五子棋大厅。所以这个名字对任何人（包括玩家自己）都不可见。让玩家为一局自己跟机器下的棋起名字，是纯摩擦。

客户端生成 `一字棋 vs AI_Hard` 这类名字满足校验。**不改后端校验**去放宽 `Name` —— 那会同时放宽人人房间，而那里名字是有意义的。

## D4. 复用 `/rooms/:id` 而不是给一字棋另做一个棋盘页

房间页已经有的东西：SignalR 连接与重连、落子、轮次与超时倒计时、认输、聊天、围观者、对局结束弹窗、音效、棋盘皮肤。这些对一字棋全部适用且全部与棋种无关。

唯一与棋种有关的是**画几格**，那就是 D1 处理的那一件事。给一字棋另做一个棋盘页，等于把上面整串东西复制一遍，然后让两份各自漂移。

## D5. 为什么不顺手把大厅参数化

`lobby.ts` 只有 38 行，而且完全没有 gomoku 硬编码 —— 参数化它其实很浅，诱惑很大。

不做的理由不是成本，是**它会动到已发布的五子棋 UX**：`/home` 在五份 web spec 里是规范路径（落地页、guard 重定向目标、`web-shell` 的导航）。把它变成 `/g/gomoku` 的重定向要一起改那五份规格，而这个变更的目标只是「让一字棋能玩上」。

把两件事绑在一个 PR 里，会让「一字棋能不能玩」和「五子棋的落地页要不要改」变成一次审查里的同一个问题。它们不是同一个问题。

大厅参数化留给下一个真正需要它的东西 —— 中国象棋（它需要人人对战），或者用户明确要一字棋的人人房间时。
