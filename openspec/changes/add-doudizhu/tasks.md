## 7. 实现记录

### 五条"斗地主落地那天会红"的断言,全都红了 —— 而那是它们的用途

内核那六个变更里,我写了五条形如「今天还没有棋种如何如何」的断言,每条都带一句"斗地主落地那天
这条会红,那时该重新想"。这次它们**全部**变红:

| 断言 | 处理 |
| --- | --- |
| `Every_registered_game_has_two_seats_today` | 按它自己注释里写的改成"每个**计分**棋种两个座位",并**另加一条**"至少有一个棋种超过两个座位" —— 否则删掉斗地主之后前者会以空循环继续绿着 |
| `No_built_in_game_deals_a_setup_yet` | → "**恰好一个**",且是 doudizhu |
| `No_built_in_game_falls_back_on_timeout_yet` | → "**恰好一个**",且是 doudizhu |
| `TicTacToe_is_the_only_unrated_versus_game` | → 两个不计分棋种,而**两者的理由不同**,分别写进注释 |
| `Rolling_back_needs_no_guard_and_this_is_why` | 见下 —— 它守的那个**理由本身**失效了 |

"恰好一个"比"至少一个"有牙:第二个棋种要设置 / 要兜底的那天它会红,而那正是该问"这两个棋种的
需求真是同一种东西吗"的时刻。

### 那条迁移断言守的是一个**已经失效的理由**

`AddGameSetup` 的 `Down` 直接删列,而当时的论证是:「`Setup` 的唯一读者是需要它的那个棋种的规则,
而回滚到本迁移之前意味着那个棋种还不存在 —— 所以不可能有非 `NULL` 的行需要保护」。

斗地主落地之后这句话不成立了。重新想的结论:**那个 `Down` 确实会毁数据**,而且比"回滚到一个没有
斗地主的构建"更难看 —— 回滚再前滚一次,列会以全 `NULL` 回来,房间还在、还像能玩,而规则在下一手
抛「This doudizhu game has no deal recorded」。

那个迁移**不能就地改**(已合并的迁移不改是硬规矩),所以处理是:把后果**演出来**并留在案上
(`Rolling_back_across_this_migration_destroys_a_deal`),外加一条盯**范围**的断言(今天只有一个棋种
会写非 `NULL` 的 `Setup`,所以"加一个带守卫的新迁移"那笔账只涉及一个棋种)。在没有部署、库随时
可删的今天,那笔钱不值得花;第二个棋种要设置的那天这笔账变大,该重新估。

### 两条真缺陷,都是测试逮到的

**一、`FormatException` 漏出去了。** `Card.DecodeMany` 对"不认识的字符"与"同一张牌两次"都抛
`FormatException`,而那不是 `DomainException` —— 于是一个畸形载荷(`play:!!!`、`play:AA`)会以未映射
异常冒出去变成 **500**,客户端看到"服务器出错了",而实际上是它自己发错了。`Parse` 现在把它转成
`InvalidMoveException`。

**二、我自己写的重复牌检查是死代码。** `DecodeMany` 早就在拦(它自己的注释就写着"早在这里拦下,
规则层就不必再想"),所以 `Parse` 里那条永远到不了。**与 `add-doudizhu-cards` 里的 `WingsAreLegal`
是同一个缺陷**,发现方式也一样:为它写的那条测试拿到了别的异常。

### 一条我写错的**理由**(结论对的)

`DoudizhuMove` 的类注释与第一版测试都说「一个裸的 `"pass"` 就是一手四张牌的合法编码」,用来论证
标签的必要性。**结论对,理由错**:`"pass"` 里有两个 `s`,而 `DecodeMany` 恰好拒绝重复的牌,所以那
一串会抛。也就是说 `"pass"` 的安全**是运气**(那个词刚好有重复字母),不是标签的功劳。

换成 `paw` / `cab` 这种没有重复字母的词,歧义就真的在那里 —— 测试现在用 `cab`,并把 `"pass"` 会抛
这件事也断言下来,免得下一个人以为那是设计。**一个正确的结论配一个错的理由,下一个人照那个理由
推下去就会走错。**

### 验收标准的第一版**比这个仓库的实际做法更强**

我写的是「`Rooms/` 与 `Games/Abstractions/` 下都不许提到这个棋种」,写成断言之后当场红在
`IGameRules.cs` 上 —— 因为 `GameKeys` 就住在那个文件里,而**五个棋种的键全在那儿**。也就是说那条
标准与 `add-xiangqi` 以来的每一次都矛盾,只是此前没人把它写成断言。

**一条从来没被执行过的验收标准,可以和实际做法矛盾很多年。**

诚实的标准分两半,现在各有一条断言:聚合(`Rooms/`)一个字都不许提;抽象层只许在 `GameKeys` 里
多一行常量。两条都先断言扫到的文件集合非空 —— 路径写错时必须失败,而不是以"没有反例"通过。
git 侧也核对了:`backend/src` 只有那两个文件动过,`+4 / -1`。

### 那一整局是怎么脚本化的

发牌是固定种子,但"谁能压谁"取决于牌 —— 所以脚本不去依赖它。座位 0 叫 3 分当地主,然后**一张一张
出单牌**,两名农民每次都过牌。它只依赖两条与牌无关的性质:**单牌永远是合法牌型**,以及**两家过牌
之后桌面清空、轮回打出那一手的人**。20 手出牌 + 38 次过牌 + 1 次叫分 = 59 步,全部走真聚合。

### 两件明确留下的东西

**一、`DoudizhuScoring.Settle` 仍然没有生产调用方。** 它算三个座位各得多少分,而那需要一处存分的
地方 —— 一条按分的榜。触发条件:那条榜落地。与 `add-idiom-dictionary` 的 `FindByWordAsync` 同形状,
而那次的教训是**端口挑对了消费者、挑错了调用路径**;这一次调用路径没错,只是消费者还不存在。

**二、32 位种子对隐藏信息的棋种偏窄。** 一个改过的客户端知道算法、看得见自己 17 张牌,可以枚举
2³² 个种子找出相符的那一个,从而算出另两家的牌 —— 一台笔记本上可行。不在本变更修,因为修它是换
洗牌算法,而那会改变所有历史对局的发牌;而这件事今天可以推迟,正是因为 `add-match-setup` 存的是
`Encode()` 的结果、不是种子。触发条件:第一次真实部署之前。
