## Why

牌、牌型、压牌、发牌、计分已经在 `add-doudizhu-cards` 落地并被证明。内核的六个使能变更也都合并了。**这个变更把两半接起来**:`DoudizhuRules` 实现 `IGameRules`,登记进注册表,然后用真 `Room` 打完一整局。

这是**第八款游戏**,也是第一个:三个座位、有隐藏信息、按分结算而不是 ELO。

## What Changes

- `DoudizhuRules : IGameRules, IDealtGameRules, ITimeoutFallbackRules`
- `DoudizhuMove` —— 一步棋的文本编码(叫分 / 过牌 / 出牌)
- `DoudizhuTable` —— 从 `(Setup, History)` 重建"这局到现在什么样"
- 登记:`GameKeys.Doudizhu`、`BuiltInGameRules.All`、DI 一行
- **不改任何内核文件** —— 这是本变更的验收标准,与 `add-xiangqi` / `add-klotski` / `add-idiom-chain` 相同

## 家规:叫分制

座位 0 先叫,然后 1、2,每人一次机会:

- 可以叫 **1 / 2 / 3** 分,或**不叫**
- 叫的分 MUST 严格高于当前最高分
- 有人叫 **3** 分则立即结束叫分(没人压得过)—— 他是地主
- 三人各一次之后,最高分者是地主;底牌归他,他先出牌

底分就是那个最高分,`DoudizhuScoring` 的 `BaseScore` 早就这么写着(「叫地主时的最高分,1 / 2 / 3」),所以这不是新决定,是把已有的假设兑现。

### 三家都不叫 = 流局(和局)

**不重新发牌。** 重发需要在同一个 `Game` 上换第二份 `Setup`,而那要改内核 —— 而「发牌在开局那一刻定下、之后不变」这条性质值得保住:它是重放与"服务端侧设置"这个概念的地基。

代价是真的:一局什么都没发生就和了。备选是"强制 0 号当地主",而那会因为一条他没选的规则罚他。**流局是把代价放在没人吃亏的地方**,而且它罕见 —— 想玩的人会叫。

## 一步棋的文本编码,以及它为什么要标签

`Move.Text` 装得下(64 字符;`play:` + 最多 20 张 = 25)。三种一步:

| 文本 | 含义 |
| --- | --- |
| `bid:0` … `bid:3` | 叫分,`0` 是不叫 |
| `pass` | 出牌阶段过牌 |
| `play:<cards>` | 出牌,`<cards>` 是 `Card.Encode` 的输出 |

**标签不是装饰。** 牌的字母表是 `A-Za-z@#`,而 `p`、`a`、`s` 都是合法的牌字符 —— 所以一个裸的 `"pass"` **就是一手四张牌的合法编码**。标签在固定位置(第一个 `:` 之前)让它无歧义。

这也是为什么标签是可读的英文而不是一个字符:`Move.Text` 会被人在数据库里读,而 `"cABC"` 与 `"play:ABC"` 差 5 个字符、差一整个"这是什么"。

## 规则从 `(Setup, History)` 重建一切

`DoudizhuTable.Reconstruct(state)` 走一遍历史,得到:

- 现在是叫分阶段还是出牌阶段
- 地主是谁、底分多少
- 三家各自**还剩什么牌**(初始手牌减去打出去的;地主再加底牌)
- 桌上现在是什么牌型、谁打的、连续几家过牌了

规则因此**无状态** —— 同一个实例被并发的多个房间共享,这是 `IGameRules` 的硬要求。每步 O(n) 重放在一局 ≤ 100 手的量级上无关紧要,与五子棋重放棋盘同一条理由。

## `NextSeat` 只用一次

叫分结束的那一手要把出手权交给**地主**,而地主可能是任何一个座位 —— 这正是 `generalize-turn-flow` 加 `MoveApplication.NextSeat` 的原因。出牌阶段的每一手都按环轮转,所以那些手数返回 `null`。

**一个字段只在一处被用到,不是浪费** —— 那一处是它存在的全部理由,而没有它,叫分与出牌之间那一步就得让内核知道"斗地主"。

## 超时兜底必须推进对局

- 叫分阶段 → `bid:0`(不叫)。三家都被托管就流局,而流局是终局。
- 出牌阶段 → 能过就 `pass`;不能过(自己是首出)就出**手上最小的一张单牌** —— 单牌永远是合法牌型,而牌只会变少。

两条都严格推进,满足 `ITimeoutFallbackRules` 写在接口上的那条要求。

## 不计分,而理由是结构性的

`IsRated = false`。ELO 是**两人**模型,而斗地主按分结算(`DoudizhuSettlement` 给出三个座位各得多少)。一个按分的阶梯是**另一条榜** —— 与俄罗斯方块的分数榜和 ELO 榜分开是同一件事。

这也让 `IsRated ⇒ SeatCount == 2` 那条不变量保持成立,不需要为斗地主开例外。**一个需要开例外的不变量已经不是不变量了。**

## 赢家是"打完手上牌的那个座位"

`MoveApplication.Won(seat)`。**不是"地主方"或"农民方"** —— `WinnerUserId` 是一个,而两名农民一起赢装不进去。

这在今天是够的:游戏不计分,`WinnerUserId` 只用于显示,而客户端从叫分历史里知道谁是地主,自己就能把"农民赢了"说出来。**真正需要"哪一方赢"的是结算**,而结算要等那条按分的榜。

## 两件明确留下的东西,各带触发条件

**一、`DoudizhuScoring.Settle` 在本变更之后仍然没有生产调用方。** 它算的是三个座位各得多少分,而那需要一处存分的地方 —— 一条按分的榜。触发条件:那条榜落地。这与 `add-idiom-dictionary` 的 `FindByWordAsync` 是同一形状,而那次的教训是**端口挑对了消费者、挑错了调用路径**;这一次调用路径没错,只是消费者还不存在。

**二、32 位种子对隐藏信息的棋种偏窄。** 一个改过的客户端知道算法、看得见自己 17 张牌,可以枚举 2³² 个种子找出相符的那一个,从而算出另两家的牌 —— 一台笔记本上可行。

不在本变更修,因为修它是换一个洗牌算法,而那会**改变所有历史对局的发牌**(种子→牌的映射变了)。而这件事今天可以推迟正是因为 `add-match-setup` 存的是 `Encode()` 的结果、不是种子:换算法只影响将来的新局。触发条件:第一次真实部署之前。
