# add-doudizhu-play-hints — tasks

## 1. 接缝(第五次用同一个模式)

- [x] `IPlayHintRules.LegalPlays(MatchState, seat)` → 牌的编码串,对内核**不透明**。
- [x] 两个牌类棋种各自实现;另外五个棋种一行不动。
- [x] `GetPlayHintsQueryHandler` **不再写死棋种键** —— 按注册表解析这个接口。
      **那是这个变更真正必须做的事**:加第二个游戏而不加接缝,Application 层就会长出
      一个 `switch (gameKey)`。

## 2. `DoudizhuFollows`

- [x] 候选是**两部分的并集**:同型同长度更大的,并上任何一个炸弹 / 王炸。
- [x] 带填充牌的六种**只列一条**,填充牌取最弱。
- [x] 炸弹**排在最后** —— 提示从最弱的一手开始,而炸弹比任何非炸弹都强、张数可能更少,
      所以「先弱后强」在跨型的候选里不是一个数能表达的。

## 3. `canFollow`

- [x] 进 `DoudizhuSeatView`,定义与挖坑逐字相同(与轮次无关)。
- [x] 客户端 adapter 读真值 —— 它此前是一个写死的 `false`。

## 4. 测试

- [x] 跨型:炸弹压任何非炸弹、王炸压炸弹、更小的炸弹压不住、桌上是炸弹时没有非炸弹候选。
- [x] 四带二不是炸弹。
- [x] 顺子只与同长度比。
- [x] 带牌只列一条 + 填充牌取最弱 + 配不齐就不产生候选。
- [x] 「要不起」那条**先断言这手牌里没有炸弹** —— 手里有炸弹就永远出得起。
- [x] `canFollow` 与候选列表逐座位一致,**两个棋种各走一遍**。
- [x] 注册表走查:恰好两个棋种实现这个接缝。
- [x] 客户端:斗地主 adapter 读真值(含负向与「服务端不发这个字段」)。

## 5. 变异

- [x] 炸弹不进候选 → Domain 4 红。
- [x] 填充牌可以与 body 同点数(那条真缺陷)→ Domain 1 红。
- [x] handler 忽略接缝 → Application 4 红。
- [x] 客户端 adapter 退回写死 `false` → 1 红。

## 6. 计划之外

- [x] **一条真缺陷,由第一次跑测试抓到:** 三带一的填充牌取到了**同点数的第四张**,
      于是 `777 + 7` 被 `Recognise` 认成**炸弹** —— 炸弹因此进了候选两次。
      填充牌必须是**别的点数**:同点数的第四张凑出来的是炸弹,不是三带一。
- [x] **提案里「客户端零改动」那句话是错的。** 斗地主那份 adapter 里 `canFollow` 是一个
      写死的 `false`,注释还写着「斗地主还没有这个功能」—— 那个占位符本来就在等这一天,
      而我把「参数化过了」记成了「不用改」。真实代价是一个字段、一处解析、一处 adapter。
      **参数化的回报是真的,只是它的单位不是零。**
- [x] **一次 `--no-build` 测了旧二进制。** 构建因为测试文件的构造调用没跟上而失败,
      而紧接着的 `dotnet test --no-build` 报了三行 `Passed!` —— 那是上一次构建的产物。
      本文件已记过这一族:**一次失败的构建后面跟一次成功的运行,和两次成功,长得一样。**
