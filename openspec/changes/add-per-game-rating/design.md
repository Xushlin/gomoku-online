# add-per-game-rating — design notes

## D1. 能力声明与 `IsRated` 已由 `add-game-capabilities` 处理

那个变更把 `IsRated` 从手工维护的判断换成了受不变量约束的声明,并解释了为什么原来记在三处的
「`add-per-game-rating` 会删掉它」是错的。理由、被否掉的备选、以及"预留合同不预留代码"那份合同表
都在 `openspec/changes/archive/2026-08-14-add-game-capabilities/` 里。

**本变更不碰 `IsRated`。** 它只做评分数据的归属:从一个全局池拆成按棋种。

## D2. `User` 上的战绩字段删掉，不留镜像

诱惑很大：保留 `User.Rating` 作为「主要棋种的分」或者「所有棋种的加权」，既有 DTO / 前端 / 搜索排序全都不用动。

不做，因为那是两份真源。这个仓库已经在两处付过同一笔学费：

- 建房的棋种校验必须走注册表，不许内联白名单 —— 两份清单迟早不一致，而不一致的那天不会有人发现。
- 前端 manifest 的 `board` 是服务端数据的**刻意副本**，之所以能接受，只因为失配症状是肉眼可见的格数不对，而且服务端会挡住越界落子。

`User.Rating` 的镜像没有这两个安全网：它和 `UserGameStats` 里 gomoku 那行漂移之后，症状是**排行榜和资料页显示不同的分**，而且没有任何东西会拦住它。

代价是本变更要动 8 个后端文件（不算迁移）和 8 个前端文件。前端那 8 个推到 `add-web-per-game-rating`；后端 DTO 用缺省 `gomoku` 让已发布客户端看到与现在完全一致的数字。

## D3. 迁移必须显式搬数据，而且顺序不能错

三步在**同一个** migration 里：建 `UserGameStats` 表 → 用显式 SQL 把每个 `User` 的五个字段搬成一行 `GameKey='gomoku'` → 删列。

顺序反了（先删列）数据就没了。而 EF 的自动生成不知道这三步有依赖关系。

这个仓库在完全一样的地方被咬过一次：`AddRoomGameKey` 那次 EF 生成了 `defaultValue: ""`，会让每一个既有房间的 `GameKey` 变成空串 → 解析不出规则 → 404 → 房间全部不可玩。那次是手工改成 `'gomoku'` 加一条显式 `UPDATE` 才对的。

所以本变更的迁移 MUST 手工检查，且 MUST 有一个测试：在一个"迁移前"形状的库上跑迁移，断言战绩一行不丢。

至于「本地 SQLite 没有生产数据，随便重置」—— 那是真的，但迁移是这个仓库里**唯一会在别人的机器上按原样跑一遍**的东西。写错了不影响我，影响下一个 clone 的人。

## D4. 没下过某棋种的人不在该棋种的榜上

选择：没有 `UserGameStats` 行 = 不出现在该棋种排行榜上。

备选是「所有人以 1200 分入榜」。不做：那样一个从没下过一字棋的人会出现在一字棋榜上，位置取决于有多少人恰好也没下过。榜的含义会从"这些人的棋力顺序"变成"这些人里谁碰巧下过"。

副作用要说清楚：一个新棋种刚上线时它的榜几乎是空的。那是**对的** —— 榜空是因为确实没人下过，不是因为查询坏了。前端需要一个真实的空状态（这在 `add-web-per-game-rating`）。

## D5. 三个阶梯依然各算各的

`CLAUDE.md` 从第一天就写着：ELO / 谜题（星数+用时）/ 计分攻关，三个阶梯刻意不统一。本变更**不动**这一点，只把 ELO 那一个拆成按棋种。

值得重申，因为「per-game rating」这个名字听起来像要统一什么。它不统一任何东西：`PuzzleLevelProgress` 一行不改，将来的分数榜也不受影响。一个成语纵横的星数和一个五子棋的 ELO 之间没有可换算的东西，硬凑一个综合分只会造出一个谁都不认的数字。

## D6. 搜索排序暂时钉在五子棋

`SearchUsers` 返回 `Rating` 用于展示与排序，而现在它必须选一个棋种。本变更取 `gomoku` 并把它记为缺口。

理由不是省事：找人卡片是**五子棋大厅**的一个组件（`pages/lobby/cards/find-player`）。让它按棋种参数化，等于开始泛化大厅 —— 而那是 roadmap 上的下一步，且会动到 `/home` 在五份 web spec 里的规范地位。一个变更做一件事。
