# add-per-game-rating — design notes

## D1. 把一个会过期的判断换成一个结构性事实

我在三个地方写下了「`add-per-game-rating` 会删掉 `IsRated`」：字段的 XML 注释、`game-rules-registry` 的一条 requirement、`UnratedGameEloTests` 的类注释，加上 `CLAUDE.md` 的 roadmap。当时的判断是：这个开关只为保护共享评分池，池子一分开它就没用了。

那个判断漏了一件事：**一字棋没有人人对战。** 它唯一的对手是机器人，而机器人对局是计分的（`add-ai-opponent` D7：不计分会让 bot 的 1200 分变成真人反复刷的提款机）。于是一字棋阶梯的榜首是刷 Easy 档最多的人 —— 不是"噪声"（我上个变更用的词太轻），是一个**可见且可刷的错误信号**。做出来比不做差。

### 但重点不是这个结论，是字段的形状

`IsRated` 是一个手工维护的布尔，语义是「要不要给这个棋种算分」。那是一个**判断**。判断会过期，而过期的判断不会报错 —— 一字棋将来有了人人对战，得有人记得回来翻它。没人记得的那天，代码和现实分岔，静默地。

这正是我上一轮踩的坑的同一形状：我在三处写下「等 `add-per-game-rating` 删掉我」，然后自己在实现下一个变更时才发现那个承诺本身是错的。**注释里的待办事项不是机制。**

所以换成：

```
SupportsHumanVsHuman : bool      结构性事实 —— 这个棋种有没有人类对手池
IsRated              : bool      判断，但受不变量约束
不变量：IsRated ⇒ SupportsHumanVsHuman        （测试强制，遍历注册表断言）
```

一字棋今天 `SupportsHumanVsHuman = false`，于是 `IsRated` **只能**是 false —— 从「我替你做的判断」变成「被不变量逼出来的」。将来它有了人人对战，翻那个结构性字段，评分从"禁止"变成"允许"；开不开是一个独立的产品决定，而不是一件要靠记性的事。

### `SupportsAi` 不加

诱惑是对称地也声明「支不支持人机」。不做：`IGameAiRegistry.For(key)` 已经知道答案 —— 注册了 AI 工厂就是支持，没注册就是不支持。加个字段等于第二份真源。

这个仓库已经为同一件事付过两次学费：建房校验必须走注册表不许内联白名单；前端 manifest 的 `board` 是刻意副本，且只因为失配症状肉眼可见、服务端还会兜底才被接受。`SupportsAi` 没有那两个安全网。

### 为什么放在 `IGameRules` 上，以及什么时候该搬走

`SupportsHumanVsHuman` 严格说不是一条"规则"（规则是行列数、连子长度、界内判定）。但 `IsRated` 已经在那儿了，而 `IGameRules` 就是 Domain 里"按棋种注册的那个东西"。为两个布尔另开一个注册表，比放在这里贵。

**门槛写在这里**：这类"平台能力"声明超过三个时，应该抽成一个独立的 `GameCapabilities` 类型或值对象，而不是继续往 `IGameRules` 上堆。届时 `IGameRules` 回到只描述盘面。

## D1b. 关于"预留接口"：我预留合同，不预留代码

你提到将来要加象棋的人人与人机、可能还有孔明棋、华容道，要求预留接口。

我不会写今天没有消费者的机制 —— 这个仓库刚刚用 `add-tictactoe` 证明了那个方向的代价：`add-game-rules-registry` 交付了一个只有一个实现的抽象，看起来干得很漂亮，而真加第二个棋种时暴露出三处漏水（建房写死棋种、大厅不分棋种、AI 层没有键），补漏的代价和游戏本身一样贵。抽象装得下它唯一的实例，什么也证明不了。

我预留的是**合同**：保证这些游戏是"加东西"而不是"改东西"，并把各自要碰的地方写清楚（见 proposal 里那张表）。三点具体的：

1. **象棋不复用 `NInARowRules`**，它要自己的 `IGameRules` 实现 —— 判胜是「将死」不是「连 N 子」。这不是缺陷，`NInARowRules` 从命名到参数就只承诺连 N 子那一族。它照样只是"一个类加一处注册"，因为注册表本身不关心你怎么判胜。
2. **象棋的人机与人人互不依赖**。`IGameAiRegistry` 与 `SupportsHumanVsHuman` 是两个独立的声明，所以象棋可以先只有人人对战（不注册 AI 工厂），或者反过来 —— 已加测试钉住"有规则但没 AI"这条路径能正常返回 404 而不是崩。
3. **孔明棋、华容道跟本变更完全无关。** 它们是单人关卡，走 `IPuzzleRules` 那条线：一个实现 + 一处注册 + 关卡数据，不碰 `IGameRules`、不碰评分、不碰 `UserGameStats`。孔明棋连"对手"都没有，"评分"这个概念在它身上不适用；它的阶梯是谜题阶梯（星数 + 用时），成语纵横已经验证过那条路能跑。

## D2. `User` 上的战绩字段删掉，不留镜像

诱惑很大：保留 `User.Rating` 作为「主要棋种的分」或者「所有棋种的加权」，既有 DTO / 前端 / 搜索排序全都不用动。

不做，因为那是两份真源。这个仓库已经在两处付过同一笔学费：

- 建房的棋种校验必须走注册表，不许内联白名单 —— 两份清单迟早不一致，而不一致的那天不会有人发现。
- 前端 manifest 的 `board` 是服务端数据的**刻意副本**，之所以能接受，只因为失配症状是肉眼可见的格数不对，而且服务端会挡住越界落子。

`User.Rating` 的镜像没有这两个安全网：它和 `UserGameStats` 里 gomoku 那行漂移之后，症状是**排行榜和资料页显示不同的分**，而且没有任何东西会拦住它。

代价是本变更要动 8 个后端文件（不算迁移）和 8 个前端文件。前端那 8 个推到 `add-web-per-game-rating`；后端 DTO 用缺省 `gomoku` 让已发布客户端看到与现在完全一致的数字。

## D3. 迁移必须显式搬数据，而且顺序不能错

三步在**同一个** migration 里：建 `UserGameStats` 表 → 用显式 SQL 把每个 `User` 的五个字段搬成一行 `GameKey='gomoku'` → 删列。

顺序反了（先删列）数据就没了。而 EF 的自动生成不知道这三步有依赖关系。

这个仓库在完全一样的地方被咬过一次：`AddRoomGameKey` 那次 EF 生成了 `defaultValue: ""`，会让每一个既有房间的 `GameKey` 变成空串 → 解析不出规则 → 404 → 房间全部不可玩。那次是手工改成 `'gomoku'` 加一条显式 `UPDATE` 才对的。

所以本变更的迁移 MUST 手工检查，且 MUST 有一个测试：在一个"迁移前"形状的库上跑迁移，断言战绩一行不丢。

至于「本地 SQLite 没有生产数据，随便重置」—— 那是真的，但迁移是这个仓库里**唯一会在别人的机器上按原样跑一遍**的东西。写错了不影响我，影响下一个 clone 的人。

## D4. 没下过某棋种的人不在该棋种的榜上

选择：没有 `UserGameStats` 行 = 不出现在该棋种排行榜上。

备选是「所有人以 1200 分入榜」。不做：那样一个从没下过一字棋的人会出现在一字棋榜上，位置取决于有多少人恰好也没下过。榜的含义会从"这些人的棋力顺序"变成"这些人里谁碰巧下过"。

副作用要说清楚：一个新棋种刚上线时它的榜几乎是空的。那是**对的** —— 榜空是因为确实没人下过，不是因为查询坏了。前端需要一个真实的空状态（这在 `add-web-per-game-rating`）。

## D5. 三个阶梯依然各算各的

`CLAUDE.md` 从第一天就写着：ELO / 谜题（星数+用时）/ 计分攻关，三个阶梯刻意不统一。本变更**不动**这一点，只把 ELO 那一个拆成按棋种。

值得重申，因为「per-game rating」这个名字听起来像要统一什么。它不统一任何东西：`PuzzleLevelProgress` 一行不改，将来的分数榜也不受影响。一个成语纵横的星数和一个五子棋的 ELO 之间没有可换算的东西，硬凑一个综合分只会造出一个谁都不认的数字。

## D6. 搜索排序暂时钉在五子棋

`SearchUsers` 返回 `Rating` 用于展示与排序，而现在它必须选一个棋种。本变更取 `gomoku` 并把它记为缺口。

理由不是省事：找人卡片是**五子棋大厅**的一个组件（`pages/lobby/cards/find-player`）。让它按棋种参数化，等于开始泛化大厅 —— 而那是 roadmap 上的下一步，且会动到 `/home` 在五份 web spec 里的规范地位。一个变更做一件事。
