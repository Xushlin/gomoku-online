## Requirements
### Requirement: 分数由服务端重放**放置序列**得出,客户端报的数字不采信

`TetrisRules` SHALL 从一个 `Seed` 与一串放置 `(PieceIndex, Rotation, Column)` 重放整局,并算出 `Score` / `Lines` / `Level`。客户端提交的任何分数字段 MUST 被忽略。

**重放的粒度是放置,不是按键。** 提交完整输入流(左/右/旋转/软降/硬降)会要求客户端与服务端两份模拟**逐帧一致**,包括重力间隔、锁定延迟、软降速率与等级曲线。任何一处差一帧,重放结果就不同,而**症状是一局合法的游戏被拒** —— 玩家看到的是「我明明打完了,它说我作弊」。这正是 `add-web-xiangqi` 拒绝把象棋规则港到 TypeScript 时给出的同一条理由:两个必须位对位一致的真源。

放置这个粒度**不涉及任何计时**:重力、锁定延迟、软降全都不进重放。每个放置可判定 —— 形状在那个列那个旋转下合法吗、落下后停在哪、消了几行。它与华容道「一次滑动」同级,而那个模型已被一款真游戏验过。

**诚实的限制**:重放保证的是**分数与放置一致**,不是**放置出自人手**。离线求解器可以按服务端给的种子算出接近最优的下法。本要求 MUST NOT 声称分数一定由人打出 —— 一个无法验证的断言比没有断言更糟(`add-xiangqi-ai` 立下的规矩)。重放的价值是把"随便报个数"降级成"你得真算出一个能拿那个分的下法"。

系统 SHALL NOT 为单局分数设置上限,也 MUST NOT 因分数高而拒绝或标记一次 run。

这是一个**明知代价的决定**,不是遗漏:任何硬上限都会**先误伤真高手** —— 分布的最右端既是作弊者也是最强的玩家,而阈值分不开它们。软上限(超过 X 就人工复核)只是把同一个判断推给一个不存在的人工流程。所以限制写在明处(上一段),而不是用一个会伤害正常玩家的机制去假装它不存在。

#### Scenario: 客户端报的分数被忽略
- **WHEN** 提交体里带 `score: 999999`,而放置序列只够 500 分
- **THEN** 记录的分数是 **500** —— 重放算出来的那个

#### Scenario: 非法放置整局被拒
- **WHEN** 序列里某个放置的列会让形状越出场地,或该处已被占
- **THEN** 提交 MUST 失败,MUST NOT 记录任何分数

#### Scenario: 同一序列重放两次得同一分
- **WHEN** 同一个 `(seed, placements)` 重放两次
- **THEN** `Score` / `Lines` / `Level` 完全相同 —— 重放 MUST 是确定性的

### Requirement: 方块序列由服务端的种子决定

`Seed` SHALL 在 run 开始时由服务端生成并下发。方块序列 SHALL 是 `seed` 的确定性函数,客户端与服务端用同一算法。

客户端 MUST NOT 能选择或影响方块序列 —— 否则它可以挑对自己有利的方块,而重放会照样通过(那些放置确实合法)。

这个生成器是本游戏**唯一容许的两份实现**,而容许的理由与别处不同:它是纯函数 `seed → 序列`,无状态、无计时,可以用一条测试逐项对齐(前 N 个方块必须完全相同)。它不一致的症状也不是"合法游戏被拒",而是"第一个方块就不对" —— 立刻可见。

#### Scenario: 同种子同序列
- **WHEN** 用同一个 seed 生成两次
- **THEN** 两次的方块序列完全相同

#### Scenario: 不同种子不同序列
- **WHEN** 用两个不同 seed 各生成前 50 个方块
- **THEN** 两个序列 MUST NOT 完全相同

#### Scenario: 七种方块都会出现
- **WHEN** 生成足够长的序列
- **THEN** 七种标准方块每一种都出现过 —— 一个只发某几种的生成器会让重放全绿而游戏不可玩

### Requirement: 周期榜按**自然周**切,不按滚动窗口

`GET /api/score-runs/leaderboard` SHALL 支持窗口 `week` / `month` / `all`,按 `ScoreRun.FinishedAt` 过滤。

`week` MUST 指**自然周**:周一 00:00 UTC 起,到下周一 00:00 UTC 止。MUST NOT 是"最近 7 天"的滚动窗口。

理由是这两者对玩家意味着不同的东西。自然周有一个**所有人共享的截止时刻**,于是"本周还剩两天"是一句对每个人都成立的话,榜单也有一个可以被谈论的结算点。滚动窗口对每个人在每一刻都不同,没有共同的紧迫感,而且一个昨天还在榜上的成绩会在今天悄无声息地掉下去 —— 玩家看到的是名次莫名其妙地变了。

代价是周一清零显得突然。接受它,因为**可预期的残忍好过不可解释的漂移**。

边界 MUST 取 UTC 而不是服务器本地时区:后者会让同一个榜在不同部署下切在不同时刻,而那是一个没人会想到去查的差异。

#### Scenario: 自然周的边界
- **WHEN** 一次 run 结束于本周一 00:00 UTC 之前一秒
- **THEN** 它 MUST NOT 出现在 `week` 榜上,即便距今不足 7 天

#### Scenario: 周内的都在
- **WHEN** 一次 run 结束于本周一 00:00 UTC 之后
- **THEN** 它出现在 `week` 榜上

#### Scenario: `all` 不过滤
- **WHEN** 用 `all` 查询
- **THEN** 返回全部已结束的 run,不按时间过滤

### Requirement: 榜上一个玩家只占一行

分数榜 SHALL 让每个玩家在窗口内**只占一行** —— 取其最高分的那一局。同一个人的多局 MUST NOT 各占一行。

一个被同一个人刷满十行的榜不叫榜。而且计分类天生鼓励反复重开(这正是它与闯关的区别:闯关一关只需通一次),所以"每局一行"的失败模式不是偶发,而是**必然**。

去重的比较 MUST 是**全序**:分数 → 结算更早 → run id。前两级几乎足够,第三级是为了让"完全同分且同一毫秒"也只留一行 —— 榜上出现同名两行,是那种看一眼就知道错了、却很难说清为什么的缺陷。

未结算的 run(`FinishedAt` 为空)MUST NOT 出现在任何窗口的榜上。它没有分数,而 `0` 是一个合法的分数,所以它也不能被当成 0 分参赛。

#### Scenario: 同一个人的四局只上一行
- **WHEN** 某玩家在窗口内有 500 / 1500 / 900 三局,另一玩家有 1200 一局
- **THEN** 榜共 **2** 行,第一行是 1500,第二行是 1200

#### Scenario: 同分同刻也只有一行
- **WHEN** 同一玩家有两局分数相同且 `FinishedAt` 相同
- **THEN** 榜上该玩家仍然只有一行

#### Scenario: 进行中的一局不参赛
- **WHEN** 一个 run 已开始但未提交
- **THEN** 它 MUST NOT 出现在任何窗口的榜上

### Requirement: 一次 run 是权威单位,且不可复用

`ScoreRun` SHALL 持有 `UserId`、`GameKey`、`Seed`、`StartedAt`、`FinishedAt`、`Score`、`Lines`、`Level` 与并发令牌 `RowVersion`。

规则与 `PuzzleAttempt` **逐条对齐**,因为要防的是同一批事:

- 已结束(`FinishedAt` 非空)的 run 再提交 MUST 拒绝 —— 客户端因此无法重复提交刷分。
- `StartedAt` / `FinishedAt` MUST 取自 `IDateTimeProvider`,MUST NOT 采用客户端上报的任何时间。
- run 只能由其所有者操作:`UserId` 不匹配 MUST 返回 **404** 而非 403 —— 不向调用方泄漏"该 id 存在"。

#### Scenario: 不能重复提交
- **WHEN** 对同一个 run 第二次调用 submit
- **THEN** 请求被拒绝,`Score` 与 `FinishedAt` 保持首次提交的值

#### Scenario: 他人的 run 不可见
- **WHEN** 用户 B 以用户 A 的 run id 调用 submit
- **THEN** 返回 404

#### Scenario: 用时取服务端时钟
- **WHEN** 客户端在提交体里带任何时间字段
- **THEN** 该字段 MUST 被忽略

### Requirement: 俄罗斯方块的规则是标准的那一套

`TetrisRules` SHALL 实现:10 列 × 20 行场地;七种标准方块(I / O / T / S / Z / J / L),每种四个旋转态;消行;计分 `1/2/3/4 行 = 100/300/500/800 × 等级`;每 10 行升一级,等级从 1 起。

计分公式写在这里而不是"随便定",因为**分数是这个游戏的全部** —— 一个非标准的公式会让所有对外的分数无从比较。

#### Scenario: 单行与四行的分差
- **WHEN** 在等级 1 消 1 行与消 4 行
- **THEN** 分别得 100 与 800 —— 四行 MUST NOT 等于四倍单行(那会让"攒四行"这个核心决策消失)

#### Scenario: 等级放大分数
- **WHEN** 在等级 3 消 1 行
- **THEN** 得 300

#### Scenario: 每十行升一级
- **WHEN** 累计消到第 10 行
- **THEN** 等级变 2

### Requirement: 计分类不新增注册表接口

本变更 MUST NOT 引入 `IScoreAttackRules` 之类的注册表接口。

理由是这个仓库的历史:`add-puzzle-core` 先造了 `IPuzzleRules`,只有成语纵横一个实现,还配了一个**形状像成语纵横的假实现**去证明接缝通用 —— 而假的无法反驳它被写下时的假设。华容道一来,`Validate` 缺 layout、`Score` 看不到步数,两处都要改(`generalize-puzzle-rules`)。

**计分类只有一款游戏在规划里。** 先造注册表是在没有第二个实现的情况下猜通用形状,而且赔率比那次更差 —— 那次至少有六款棋在路上。

`ScoreRun` 命名为通用的,因为它是**数据**而不是接缝:数据形状错了改一列,接缝形状错了改每个实现。

第二款计分游戏出现那天,内核从**两个真实现**之间长出来。

#### Scenario: 代码里没有计分类注册表
- **WHEN** 审阅本变更引入的类型
- **THEN** MUST NOT 存在 `IScoreAttackRules` / `IScoreAttackRegistry` 或等价物

#### Scenario: 也没有假实现来证明通用性
- **WHEN** 审阅本变更的测试
- **THEN** MUST NOT 存在一个"为了证明接缝通用"而写的第二个计分游戏假实现
